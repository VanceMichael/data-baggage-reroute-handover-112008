# 跨航司签转时的行李交运工作台

旅客签转后，原航司与新航司的现场人员都可能需要查明“这一件行李现在该由谁接”。本项目采集票务、分拣、受理、班次与现场报表，逐件给出**可交接 / 待确认 / 必须人工处理**的判断、证据缺口和下一步联系人，并提供交接指令的认领、交班与关闭记录。

它**不订票、不改签、不向行李设备下达装机命令**，也不替任何一边决定行李能否抽回；所有输出只用于地服查阅与联调。

## 本地运行

使用 Node.js 22.23.4，项目只使用随 Node.js 提供的运行库。

```sh
# 终端一：合成来源
npm run source            # 默认 http://127.0.0.1:4173

# 终端二：工作台
npm start                 # 默认 http://127.0.0.1:4180，来源默认 4173
npm test
```

工作台地址 `http://127.0.0.1:4180/`。环境变量：

| 变量 | 作用 | 默认 |
| --- | --- | --- |
| `APP_PORT` / `PORT` | 工作台端口 | `4180` |
| `SOURCE_PORT` | 本地合成来源端口 | `4173` |
| `SOURCE_URL` | 直接指定来源地址（优先于 `SOURCE_PORT`） | `http://127.0.0.1:4173` |

来源演练时钟可用 `PUT /_source_clock?step=dispatch` 推进，阶段为 `book`、`dispatch`、`receive`、`withdraw`、`correction`。每次打开工作台或调用 `GET /api/snapshot` 都会重新采集当前阶段，因此可以按阶段观察同一批行李的变化。

## 判断规则

- **逐件追踪**：以旅客托运行李的**原始条码**为唯一键。新条码只记入本件收件记录，绝不覆盖原条码；同一旅客分次托运的多件行李各自判断。
- **不合并**：不按航班号、姓氏或新票条码把不同旅客人或不同来源的行合并。分拣记录必须同时匹配航段与旅客代号，否则不归属。
- **时间只在本件内比较**：不同来源的采集时间（`seen`）不构成全局序列。先后关系用对应航段、交运编号、分拣点序号与可核对的现场动作时间（`at`）解释。
- **受理的三种空/异常**：空页且未完成 → 受理未开始；空页却标记完成 → 空白受理页待核实；有行但未列本件 → 收件凭据缺失；`accepted:false` → 明确拒收。这几种不会互相代替。
- **重传扫描**：同一分拣点、同一条码、同状态、同动作时间的重复行按一次现场动作处理，仅标记为重传，不叠加次数。
- **装机无法确认可抽回**：本件立即停住自动交接依据（`hold`），同组其他行李照常处理。它不会因为别件已收件而连带停住。
- **签转撤销**：票务撤销不会让已收行李自动回到原航司。若新航司已有收件凭据，本件进入必须人工处理，并显示哪一边持有实体凭据。
- **晚到补传**：新航司逐件收件之后，旧分拣点补传的“待交运”记录若其**现场动作时间早于**收件，则不改变责任，只在观察中保留。晚于收件的待交运扫描则视为实体冲突。
- **班次**：按 `at` 选择当前班次。已收件签收人若属上一班次仍视为有效凭据，后续由当前班次跟踪；与班次表不符且无历史匹配时才降为待确认。

## 交接指令

交接指令是**地服的操作认领记录**，不是装机命令。所有变更写入事件流水。

- 指令绑定到“本件 + 本次交运链（受理批次）”。同一**原条码**同一时刻只能有一条有效指令（`pending` 或 `claimed`）。
- 只有状态为**可交接**且未停住的行李才能建立指令；被停住或非可交接的会被拒绝。
- 认领后由原操作人跟踪，直到出现现场凭据或完成双方转交。已认领指令交接给接班人需要**原操作人与接班人双方确认**；待认领指令只需交班即进入接班人队列。
- 关闭必须有匹配本交运链的现场凭据（新航司收件行，或双方签署的现场确认）。没有凭据不能关闭。
- 若行李在指令存续期间因撤销、装机冲突等原因不再可交接，指令自动**失效**（`invalidated`），并保留建立当时所依赖的证据快照。

## 现场双边确认

工作台可登记“退接 / 转交”事实：必须写明交出方、接收方，且 `acceptedBy` 同时包含双方，否则拒绝。登记会并入现场报表参与下一次判断，但不会修改票务，也不会触发任何设备动作。

## HTTP 接口

| 方法与路径 | 说明 |
| --- | --- |
| `GET /` | 工作台页面 |
| `GET /api/snapshot[?refresh]` | 当前逐件判断、来源状态、指令与确认 |
| `POST /api/refresh` | 重新采集 |
| `GET /api/bags/:transfer/:tag` | 单件详情与该件指令 |
| `POST /api/instructions` | 建立指令（`transfer`、`originalTag`、`operator`、`shift`） |
| `POST /api/instructions/:id/claim` | 认领 |
| `POST /api/instructions/:id/handover` | 交班（已认领需 `acceptedBy` 含双方） |
| `POST /api/instructions/:id/close` | 凭现场凭据关闭 |
| `POST /api/instructions/:id/revoke` | 撤销指令 |
| `POST /api/confirmations` | 登记双方确认的退接/转交 |
| `GET /api/instructions` | 指令、确认与事件流水 |
| `GET /api/confirmations` | 本地登记的双边确认 |

工作台表单在无 JavaScript 时也能通过服务端表单路径完成同样操作。

## 来源约定（联调）

票务 `/tickets/transfers` 按旅客代号与会话航段发布签转、重开与撤销。分拣 `/sorting/batches` 提供批次页地址，`/sorting/S8?page=1` 的 `next` 用于沿着批次页翻页（不推测页号），序号按分拣点各自递增。`/receiving/handoffs` 列出接收批、旧原条码与可能的新条码，逐件可独立填报，`at` 为签收时间，`seen` 为来源采集时间；同一个受理来源也可能同时暴露多个批次，工作台按批次边界判断。`/shifts/handover` 给出班组与联系人编号，`/reports/manual` 是可能晚到的地服双边确认。

来源网页可能停在不同的批次、短暂不可读或仍在写入，采集按来源分别记录可用性；读取失败会显示为“待确认/来源问题”，不会把缺失当作“没有行李”。
